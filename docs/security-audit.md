# Application security audit events

Security audit events are emitted through `console.log` as single JSON lines with
`securityAudit: true` for OpenTelemetry to collect and send to Grafana. The injected `deps.log`
logger routes these lines to the console without a text prefix. Audit logging does not read or
write Deno KV. Storage, retention, access control, and queries belong to the external log backend.

Each event includes its schema version, generated event ID, UTC timestamp,
server-generated request ID, category, action, outcome, actor, and target. HTTP outcomes also
carry a status. The response's `X-Request-ID` is generated by the server and ignores any
client-supplied request ID. Correlate an attempt and its result using that request ID and action;
bulk operations also have an attempt and result for each target.

Actors are authenticated wallet addresses, or `null` for unauthenticated/early failures.
Successful sign-in records the verified wallet; a failed signature never establishes an actor
from its claimed address. Wallet targets retain valid public addresses. Other identifiers
(proposal selectors, session inventory IDs, comments, filenames) are SHA-256 hashes; operators
can hash a known identifier to find the related events. These hashes are correlation identifiers,
not anonymization for low-entropy values.

The schema deliberately excludes request/response bodies, SIWE messages and signatures, session
tokens and their hashes, cookies, authorization headers, claim tokens, private proposal content,
IP addresses, user agents, arbitrary paths, query strings, URLs, and raw error messages/stacks.
Details are restricted to known operations such as `approve` or `reauthenticate`. Application
services may still produce separate diagnostic logs; apply independent access and redaction
policies to those logs as well.

## Events and mutation behavior

Coverage includes sign-in success/failure, reauthentication, cookie migration, logout,
individual/per-wallet/global revocation, role grants/removals, authorization and Origin denials,
validation rejection, rate limiting, unexpected request failures, and administrative changes to
initiatives, revisions, pledges, donations, Safe bindings, comments, logos, and content sync.
Administrative edits through proposer-facing endpoints are included. Every administrative
mutation route has a fallback event if a specific classification has not yet been added.
Status changes and comment/content bulk operations include each item's outcome, and aggregate
outcomes distinguish partial success. A pending Safe deployment is recorded as pending.

Sensitive operations emit an attempt before their handlers run and an outcome when they finish.
Logging is best effort: a logger or downstream delivery failure does not block a mutation or
replace its response with a 503. There is no local durable copy or delivery acknowledgment.
An attempt without a result does not prove the mutation failed. Content sync can update an
initiative before a later backer step fails; an item failure similarly does not promise rollback.

## Access and controlled verification

Only an administrator with recent SIWE authentication can use the controlled test endpoint:

- `POST /api/admin/audit/test` emits a harmless fixed `audit.test` attempt and success event.
  Send an empty body or `{}`. Use the returned `X-Request-ID` to locate
  the events in Grafana. A successful response confirms the request succeeded, not log ingestion.

The application has no audit-history endpoint; query the external log backend for past events.

Use an existing authenticated session in staging to invoke the test endpoint; do not paste
credentials into a URL, shell history, ticket, or log query. Verify that an ordinary wallet is
denied access. The automated regression command is:

```sh
deno test -A api/tests/audit.test.ts
```

These tests capture the JSON log lines and exercise redaction, access control, the absence of
audit KV access, and unchanged mutation/error responses when logging fails. They do not attest
production collection configuration or downstream alerts.

## Production collection and alerting

Configure the runtime's OpenTelemetry log export to the Grafana log backend, retaining the JSON
body so `securityAudit`, `requestId`, `action`, and `outcome` can be queried. Restrict reader access
and exporter credentials, and configure storage protection and retention in that backend.

Configure alert routing for `session.admin_revoke_all` and
unexpected role change; repeated `auth.verify` failures, `authorization.denied`, `abuse.limited`,
and `request.failed` should trigger thresholds appropriate to measured traffic. Alert on stale
attempts without completion after allowing for normal request duration. Collector ingestion
health must be monitored independently, since a broken collector cannot report its own outage.

To verify alert routing, temporarily route `audit.test` success events to the intended on-call
destination, call the controlled endpoint, correlate its request ID in Grafana, confirm receipt,
record the evidence, and remove the temporary test rule. Verify clock synchronization, backend
retention, access restrictions, and collection health in staging.

**OpenTelemetry export, Grafana ingestion, external retention, and on-call alert
routing have not been configured or verified by this code change.** These are deployment tasks;
passing local tests alone does not close the report's operational assurance requirements.
